 1. Abstract 摘要

A. Attention Getter — Motivation 台電預估 2026 年夏季尖峰負載達 4,294 萬瓩、夜尖峰達 3,853 萬瓩，皆
創歷史新高，較 2025 年尖峰 4,092 萬瓩增加約 4.89%，主因是半導體與 AI 用電成⾧ [7]。供給端同樣不穩：
2025 年 9 月興達新 2 號機試運轉時發生爆炸 [12]，林口 2 號機又故障，台電表示近日共減少 210 萬瓩，
約為夜尖峰的 6% [10]。經濟部預估 2025 至 2029 年尖峰備轉容量率落在 11.3% 至 14.2%，低於 15% 的規
範；報導也指出機組故障曾使備轉從預估的 14% 掉到最低約 4% [9]。

B. But — Challenge 電力營運資料雖然免費公開，卻有三個缺口。第㇐，每日備轉容量率主要是調度後的
結果，我們的初步探索顯示它與氣溫幾乎無關（相關係數約 −0.07），單靠時間序列或天氣模型無法直接
預測。第二，備轉的定義本身有爭議：日尖峰與夜尖峰不同 [4]，備轉容量中慢速機組與光電的占比也受
到質疑 [14]。第三，近年的 LLM 電網 Agent 多以模擬電網與潮流求解器為對象 [20][21][22]，缺少㇐個以
台灣公開營運資料為基礎、能回答「若某部機組跳機，備轉與燈號會如何變化」的風險推演工具；而
LLM 在安全關鍵場景存在幻覺風險 [24]。

C. Cure — Proposed Solution 為了解決上述問題，本專題提出㇐個新的台電備轉風險情境推演 Domain AI
Agent（GridReserve Agent）。

D. Development — Method 系統整合四類資料：台電每日供需與近三年備轉資料、三個氣象站日觀測、台
電水火力機組設備資料，以及官方未來二個月預測。分析面以氣象與日曆特徵預測尖峰負載並給出預測
區間；領域知識面建立供電燈號規則、機組知識庫、備轉品質與「備轉 ÷ 最大單機容量」指標；Agent 面
由規劃器調用上述工具，進行預測、情境推演與事故歸因，並以驗證關卡確保輸出數字全部來自工具結
果。

E. Experiments — Evaluation 預計以 2023-01-01 至 2026-08-31 共 1,339 天的資料，以滾動時間切分評估負
載預測，Baseline 包含月平均、日曆模型與無氣象模型；以 2025 年 9 月興達與林口事故做情境推演的回
測案例；並設計約 40 題的問答集，比較「純 LLM」與「本 Agent」的數字正確率、依據可追溯性與拒答
適切性。

 2. Introduction 緒論

  A. Attention Getter

2026 年 3 月，台電公布夏季尖峰負載預測 4,294 萬瓩、夜尖峰 3,853 萬瓩，雙雙創高，並說明日尖峰備轉
要維持 10%、夜尖峰維持 7% 以上；台電同時規劃今年有四部大型新機組陸續併聯，總容量超過 500 萬瓩
同時進入試運轉，規模前所未有 [7]。2026 年 4 月，台電董事⾧再次表示夏季夜尖峰將突破 3,800 萬瓩，
並保證備轉容量率可維持 7% [8]。


  B. Background

電力系統必須即時平衡供給與需求。台電以「備轉容量」衡量當日實際可調度的供電餘裕，定義為系統
運轉淨尖峰供電能力減去瞬時尖峰負載；備轉容量率則是備轉除以瞬時尖峰負載。供電燈號依此分級：
備轉容量率 10% 以上為綠燈，6% 至 10% 為黃燈，6% 以下為橘燈；備轉容量 90 萬瓩以下為紅燈，50 萬
瓩以下為黑燈 [11]。台電的歷年統計註明，備用容量率自民國 111 年起以夜間備用容量率呈現 [4]。

本專題的資料來自電網與氣象的感測量測網路。台電的營運資料來自其電能管理系統 (EMS) [30]，氣象資
料來自中央氣象署的觀測站 [6]。使用者包含電力與能源領域的研究者、政策分析人員，以及關心供電情
勢的公眾。


  C. Problem

本專題要解決的核心問題是：如何用台灣的公開營運資料，讓使用者可以查詢、推演並理解備轉風險，
而且每個數字都有依據。 具體包含三件事：（1）預測未來尖峰負載；（2）在機組停機情境下，推演備
轉容量、備轉容量率與供電燈號；（3）對已發生的低備轉日，指出主要貢獻機組。


  D. Existing Limitations

    1. 直接預測備轉容量率並不可靠。 初步資料探索（1,339 天）顯示：尖峰負載與三站平均最高氣溫
         的相關係數約 0.75，但備轉容量率與氣溫的相關係數僅約 −0.07；淨尖峰供電能力與負載的相關
         係數約 0.92，也就是供電能力會隨負載㇐起被宣告與調度。單純用天氣預測負載、再套用前㇐週
         的供電能力推算備轉，誤差反而比直接猜平均值更大。

    2. 備轉數字不等於風險。 以 2022 年 513 與 517 停電為例，當時備轉容量雖有 10%，但可快速起停
         的機組只約占 2%，其餘需要數小時升載；517 事件中，備轉估計被高估，因為燃煤機組重啟、抽
         蓄水力用盡、太陽光電下山 [14]。
    3. 官方預測與實際之間有落差。 報導指出，機組故障曾使備轉容量率從預估的 14% 掉到最低約
         4%[9]。
    4. 現有 LLM 電網 Agent 的對象不同。 GridMind、X-GridAgent、Grid-Agent 以最佳潮流、事故分析與
         違規修復為主 [20][21][22]，其依賴的是電網模型與求解器；綜述指出領域資料有限、可靠度與可
         解釋性是主要挑戰 [23]，另㇐份綜述指出多數預測研究只最佳化單㇐誤差指標，沒有考慮決策情
         境，且 LLM 在安全關鍵場景有幻覺風險 [24]。


  E. Innovation

    1. 以公開營運資料為基礎的備轉風險情境推演，而不是模擬電網的潮流分析。
    2. 把容易預測的部分（負載）交給機器學習，把不易預測的部分（供電側）交給情境推演與領域規
         則，避免硬預測備轉容量率。
    3. 燈號規則兩套邏輯分開處理（比率與絕對值），並引入「備轉 ÷ 最大單機容量」的直觀指標。
    4. 工具約束與驗證關卡：LLM 不產生數字，所有數字必須可追溯到資料與程式輸出；超出資料涵蓋
         範圍時安全拒答。
    5. 資料品質作為貢獻：發現並修正公開資料中的備轉容量率錯誤值（見第 5 章）。


  F. Contributions

    1. 設計並實作㇐個整合負載預測、情境推演、事故歸因的備轉風險 Domain AI Agent。
    2. 建立可重複使用的台灣電網領域知識庫：供電燈號規則、機組設備表（含補充的新機組）、備轉
         品質與日夜尖峰規則。
    3. 提供資料清洗與驗證流程，並公開 6 筆已發現的資料錯誤與修正方法。
    4. 設計「純 LLM 對工具約束 Agent」的評估集，量化幻覺與可追溯性。
    5. 提出可交接的 GitHub、README.md 與 DESIGN.md，使他人能重現並延伸。

《天下雜誌》英文版另有針對 2025 年供電吃緊的討論，如 2025 年夏季晚上時備轉容量最低可能達到

(3) 鴨子曲線與機組排程。 台灣的機組排程研究預估高再生能源滲透率會使日負載曲線呈鴨子型，抽蓄水

  3.4 研究缺口歸納

Existing Research → LLM 電網 Agent 以模擬電網的潮流與事故分析為主 [20][21][22]；台灣的預測研究以負
載預測為主 [26][27]；規劃層研究處理鴨子曲線 [28][29]。

Limitations → 這些研究不會把台灣公開營運資料、燈號規則與機組知識組合成「可詢問的備轉風險推
演」；預測研究也不處理「備轉是調度結果」的問題；LLM 的幻覺與可追溯性仍是挑戰 [23][24]。

Research Gap → 缺少以台灣公開營運資料為基礎、能預測負載、推演機組停機情境、解釋燈號，且數字
可追溯的 Domain AI Agent。

Our Project → GridReserve Agent：機器學習負責負載，領域規則負責燈號與機組情境，LLM 負責理解、規
劃與解釋，驗證關卡確保數字可追溯。

     •   觀點 A：可以拆成熱機與冷機，把熱機備轉降到 6%，再加上冷機備轉 4% [16]。

  5.1 System Architecture 系統架構

  5.2 各模組說明

① 使用情境。 三類使用者：電力與能源研究者、政策分析人員、關心供電的公眾。典型問題如「明天尖
峰負載大約多少」、「若通霄某部機組跳機，備轉容量率會變成多少、亮什麼燈」、「2025 年 9 月 23 日
備轉為什麼那麼低」。

② 查詢輸入。 自然語言加結構化參數（日期、電廠或機組、情境、尖峰類型）。

③ 規劃與推理 Agent。 以 LLM 為規劃器，將查詢分為四種意圖：FORECAST（預測）、WHATIF（情境推
演）、DIAGNOSE（事故歸因）、EXPLAIN（解釋燈號與概念），拆解子任務後調用工具。超出資料涵蓋範
圍（日期、夜尖峰、民營電廠）時安全拒答並說明原因。

④ 資料取得與清洗。 讀入六個 CSV（含三個氣象站）後，套用以下規則：

    1. 備轉容量率㇐律重算為「備轉容量 ÷ 尖峰負載 × 100」（主檔有 6 筆此欄數值異常，如 202.0 應
         為 20.2）。
    2. 降水量的 −9.8 代表微量降雨，轉成 0；氣壓等不使用的欄位直接捨棄。
    3. 排除全為 0 的機組欄位（核㇐、核二、核三 #1、麥寮 #2 等 6 欄）。
    4. 單位統㇐為萬瓩（機組設備檔為瓩，需 ÷ 10,000）。
    5. 日期由 YYYYMMDD 整數轉為日期型別；近三年檔（2023-01-01 至 2025-12-31）與主檔（2025-01-
         01 至 2026-08-31）合併，重疊的 2025 年用來互相驗證。

⑤ 分析引擎。

    •    負載預測： 特徵為日曆（星期、月份、假日、趨勢）與三站氣象（最高、平均氣溫、溫度、降水、
         日照）；模型從嶺回歸、梯度提升開始，輸出 10%、50%、90% 分位數，再用 conformal 方法校準
         區間。
    •    低備轉日偵測： 以備轉容量率低於 10%（黃燈以下）為事件，搜尋歷史上的低備轉日。
    •    歸因： 事件日與前 7 周中的同㇐天平均比較，列出出力變化最大的機組群組。注意出力不等於可
         用容量，歸因結果須標註此限制。
    •    防資料洩漏： 當日的機組、太陽能、風力出力不得用於預測，只用於事後診斷。

⑥ 領域知識。

    •    供電燈號規則實作為設定檔（絕對值與比率兩套邏輯）[11]。
    •    機組知識庫：175 部機組、約 2,963 萬瓩 [5]，再補充興達新機組（三部，共 390 萬瓩 [18]）；台
         中新 1、2 號機容量皆為 130 萬瓩 [31]。
    •    備轉品質標註與「備轉 ÷ 最大單機容量」指標；最大單機為台中新 1、2 號機，容量皆為 130 萬
         瓩。
    •    文件庫（RAG）：本提案的公開報導與資料說明，供解釋時引用。

⑦ 情境推演與驗證。 備轉容量 R = S − L，其中 L 為預測負載，S 為參考供電能力（官方預測或近期同星期
中位數）扣除情境中的停機容量。備轉容量率 r = R ÷ L。燈號由規則判定。驗證關卡檢查：每個輸出數字
都對應工具輸出的編號、單位、日期。未通過則重新生成（最多 2 次），仍失敗則安全失敗。

⑧ 輸出與互動。 以 Streamlit 介面顯示結論卡、表格、圖表、資料依據、不確定度與限制，支援追問。

  5.5 Pseudocode
   Algorithm 1: GridReserve Agent
   Input : User Query Q
   Output: Grounded Result R

   01: Receive user query Q
   02: Parse intent I in {FORECAST, WHATIF, DIAGNOSE, EXPLAIN} and entities E (date range, units, scenario)
   03: if E is outside data coverage (dates, night peak, private plants) then return SafeRefusal(reason)
   04: Plan subtasks P = Decompose(I, E)
   05: D <- LoadAndClean(sources)            // recompute reserve rate, trace rain -> 0, kW -> 10^4 kW
   06: for each subtask t in P do
   07:     if t is LoadForecast then (L_hat, band) <- ForecastLoad(E.dates, weather, calendar)   //
   quantiles 10/50/90 + conformal
   08:     if t is Scenario     then S_adj <- RefSupply(E.dates) - sum(capacity(u) for u in E.outage_units)
   09:     if t is Diagnose     then top_k <- Attribute(E.date, baseline = same weekday, last 7 weeks)
   10: end for
   11: R_cap <- S_adj - L_hat; r <- R_cap * 100 / L_hat
   12: light <- ClassifyLight(R_cap, r)       // Algorithm 2
   13: n1 <- R_cap / MaxUnitCapacity(KB)      // reserve in units of the largest single unit
   14: notes <- Retrieve(KB, I, light)        // reserve quality, day/night, caveats
   15: for attempt = 1 to 3 do                // max. 2 retries, or up to 3 attempts total
   16:     R <- Compose(results, notes, citations)    // LLM writes text, numbers come only from tool
   outputs
   17:     if Verify(R, tool_outputs) then break    // every number traceable; units and dates checked
   18: end for
   19: if not verified then return SafeFailure()
   20: return R with evidence, uncertainty, limitations



   Algorithm 2: ClassifyLight
   Input : reserve capacity R_cap (10^4 kW), reserve rate r (%)
   Output: light color

   01: if R_cap <= 50 then return BLACK
   02: if R_cap <= 90 then return RED
   03: if r <= 6 then return ORANGE
   04: if r < 10 then return YELLOW
   05: return GREEN
